# VibeBench

Лещенко Ольга Сергіївна, ІО-31.

VibeBench є стендом реєстрації механічних коливань. Майбутнє вимірювальне вікно починається кнопкою, потенціометр задає поріг, а MPU6050 дає прискорення. UART виводитиме пік відхилення та кількість окремих перевищень. Частотний спектр і діагностика несправностей не входять у план.

Середовище: Ubuntu 24.04, Docker, STM32 HAL, Wokwi. Віртуальна плата Nucleo-C031C6. Фізичного обладнання немає.

## Стан ЛР1

Готовий HAL-шаблон містить USART2 115200 8N1, повідомлення `STM32C031C6 ready`, періодичні `tick` і LED на PA5. I²C1 ініціалізовано на PB8/PB9, але датчиків і вимірювальної логіки немає. ADC не налаштовано. Прошивка, .ioc та diagram.json збережені без змін.

Дві чисті Docker-збірки на Mac пройшли, SHA256 ELF/HEX/BIN збігаються. Чиста збірка в Ubuntu також пройшла. HEX і BIN збігаються з Mac; ELF відрізняється лише відлагоджувальною секцією .debug_str у libgcc. Підсумкові хеші та пояснення наведені в [результатах збірки](docs/build-checks/README.md). Симуляцію Wokwi ще не підтверджено реальним запуском. Вимоги ЛР2 і PDF-звіт ще не виконані.

## Збірка

Docker має працювати без sudo. З кореня цієї папки:

```sh
docker --version
docker info
make clean
make build
ls -lh firmware/build/firmware.elf firmware/build/firmware.hex firmware/build/firmware.bin
```

`make clean` видаляє firmware/build. `make build` перевіряє Docker-образ і запускає ARM GCC у контейнері з UID/GID поточного користувача. ELF є програмою із символами, HEX і BIN є форматами машинного коду. Артефакти не входять у Git. Dockerfile є у docker/, джерела HAL у firmware/.

## Wokwi

Відкрити саме цю папку у VS Code з установленим Wokwi і вже доступною ліцензією. Після збірки натиснути F1 та вибрати `Wokwi: Start Simulator`. Шляхи wokwi.toml ведуть на `firmware/build/firmware.hex` і `.elf`. У схемі одна Nucleo та UART-з'єднання із serial monitor.

Очікуваний результат: один стартовий рядок `STM32C031C6 ready`, послідовні `tick` приблизно щосекунди і зміна стану LED PA5. Повний цикл LED триває близько 2 с. Перший tick може бути нульовим, бо прошивка друкує HAL_GetTick()/1000. Це очікування з коду, фактичний вивід треба зафіксувати під час демонстрації.

## Документи

- [PRD](docs/PRD.md) містить 12 вимог і тести вимірювального вікна.
- [Компоненти](docs/hardware-components.md) відокремлюють фактичну HAL-конфігурацію від майбутньої схеми.
- [Правило підрахунку](docs/event-counting.md) пояснює тривале перевищення та повторний епізод.
- [План ЛР1/ЛР2](docs/roadmap.md) визначає наступні роботи.
- [Реальні перевірки збірки](docs/build-checks/README.md) містять логи, хеші та межі підтвердження.

У ЛР2 потрібно додати GPIO-кнопку, I²C MPU6050 та ADC-потенціометр, замінити секундну затримку на опитування 10 мс і виконати числові та інтеграційні тести. Порогові значення з PRD є початковими припущеннями.
